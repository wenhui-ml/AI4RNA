# Submission artifacts

Everything here is **generated by `build.sh`**, never hand-assembled, so a stale artifact is impossible as
long as that script is what produced it. Re-run it after any edit to the manuscript or any new sweep:

```bash
cd paper/chomsky_climb && ./submission/build.sh
```

The script aborts rather than shipping if the manuscript has overfull boxes or if the code supplement exceeds
the venue size limit. Both have bitten this project before.

---

## `arxiv/` — arXiv source package

| file | why it is here |
|---|---|
| `chomsky_climb.tex` | the manuscript |
| `references.bib` | for completeness; arXiv does not use it |
| `chomsky_climb.bbl` | **required.** arXiv does not run bibtex, so the bibliography must be pre-built |
| `figs/*.pdf` | only the figures the manuscript includes, resolved from `\includegraphics` at build time. The repo holds others from earlier revisions; shipping them would be dead weight |
| `00README.XXX` | engine directive (pdflatex) |

Verified by compiling the package in a clean directory with no access to the repo: zero errors,
zero missing-file warnings. Do that again after any change, because a package that builds *here* and not
*there* is the classic arXiv failure and it is invisible until upload.

**The upload archive is built for you**: `submission/chomsky_climb_arxiv.tar.gz` (344 KB, 8 entries, `.tex`
at the archive root where arXiv expects it). `build.sh` then extracts it into a scratch directory with no
access to this repo and compiles it there; the build aborts if that fails. Two traps this closes: `tar . 
--exclude='.*'` excludes the `.` entry itself and silently ships an empty archive, and tarring one level too
high buries the `.tex` inside a folder, which arXiv rejects after upload rather than before.

## `aaai/` — venue submission (AAAI field names)

| field | file | status |
|---|---|---|
| PDF | `main.pdf` | 51 pp |
| Code and Data Supplement | `code_and_data.zip` | **~2 MB** against a 50 MB limit |
| Reproducibility Checklist | `reproducibility_checklist.md` | answers below; convert to PDF at submission time |
| Technical Supplement | — | **not built, deliberately: see below** |

### The supplement is ~2 MB, and that is the interesting number

It holds every logged run behind every number in the paper: `runs/cc_ascent/` in full (per-target JSON for
all sweeps, the analysis outputs, the frozen agent-written operator sources) plus the harness source needed
to re-execute them. JSON compresses ~10:1, so the run data ships small. There was never a reason to subset
it, and we did not.

**The source list is computed, not curated.** An earlier revision named five files chosen by reading the
manuscript, and the supplement did not run: the analysis scripts import `benchmarks.rnainvbench`, which
imports `..constraints`, which nobody had listed, and no `__init__.py` shipped at all, so the package was not
importable in the first place. `collect_code.py` now walks the import graph from every entry point, so a new
import ships its target automatically. `build.sh` then extracts the zip into a scratch directory with no
access to this repo, imports every analysis script there, and re-derives the positive control's `0.293`; it
aborts if any of that fails. This is the same discipline as the arXiv clean-room compile, and for the same
reason: a supplement that works here and not there is invisible until a reviewer tries it.

### Why there is no Technical Supplement

AAAI's technical supplement exists because a 7–9 page main paper cannot carry proofs, full tables and
ablations. **This manuscript has a 32-page body**, so the split that field expects would require cutting the
body by roughly two thirds — which means dropping either the formalisation (§4, the whole negative side) or
the seven interventional attribution tests (§5.3, the most portable result). Neither is a formatting decision.

So the honest state is: **this paper is not currently in AAAI shape, and the artifacts here reflect that.**
It is in shape for arXiv and for a venue with a journal-length limit. If AAAI becomes the target, the split
is a content decision to be made first and packaged second, not the other way round.

## `rebuttal/` — artifacts for the response period

### `claim_index.md`

Every headline number, the script that produced it, and the committed output a reviewer can open. Generated,
and self-checking: each row verifies that the value still appears in the manuscript and that the named output
file exists, emitting **FAIL** rather than dropping silently. Current state: 29 claims, 0 failures.

The point is latency. The most expensive rebuttal question is "where does this number come from?" and the
most damaging answer is a delay. This answers it in one hop.

### What to add here when reviews arrive

Keep one file per reviewer point, named `R<n>_<slug>.md`, each holding the question, what was run, and the
output path. That is what made the previous three rounds tractable: the responses that landed were the ones
with a committed artifact behind them, and the ones that cost time were the ones needing a fresh sweep.

## Standing hazards, recorded because each has already cost us once

1. **Duplicated prose survives every automated check.** A 359-word block appeared verbatim in two appendices
   and passed label, reference and number checks for a full revision. `build.sh` does not catch this either.
   Read the assembled PDF before submitting.
2. **Wide cuts delete neighbours.** Two edits in the compression pass silently removed the 100-target family
   grid and a table plus an appendix section, because they sat between the two anchors being replaced. Both
   were recovered from git only because the dangling-reference check fired.
3. **Numbers must come from the logged runs.** No measured number is ever typed into the manuscript by hand;
   the claim index exists to keep that true.
